# k8si v0.9.0 goals

Findings from a full-codebase code review + QA/testing review on 2026-08-13, covering
`k8si/operator/*`, `k8si/backends/*`, `k8si/backup.py`, `k8si/restore.py`, `k8si/ui/*`,
`deploy/*.yaml`, and the test suite. Ordered by severity, most severe first.

---

## Critical

### 1. Backend failures are silently reported as success

**Problem:** `k8si/backup.py:44-109` (`_run_cycle`) catches `BackupError` on every failure path,
logs it, and `return`s instead of raising. The container exits 0, the K8s Job reports
`Complete`, and the operator patches `lastBackupResult=success`. A wrong `RESTIC_PASSWORD`, an
unreachable SFTP host, or any other backend failure looks identical to a healthy backup on the
dashboard and in Prometheus, forever — the only trace is a WARNING log for an unparseable
snapshot ID.

**Fix:** `raise`/`sys.exit(1)` after logging in `_run_cycle`. Treat "no parseable snapshot ID"
in `workflow.run_backup` as a failure, not a warning.

**Related:** The auto-init (`"repository does not exist" in e.stderr`) and unlock-retry
(`"lock" in e.stderr.lower()`) branches in `backup.py:56,64` string-sniff `stderr`, but kopia
puts that phrase in the exception message, not `stderr` (`kopia.py:64`) — so those branches
never fire for kopia and fall into the swallowed-failure path above. Existing unit test
fabricates the exception directly, masking this. Raise typed exceptions
(`RepositoryNotInitializedError`) from each backend instead of string matching.

---

### 2. Unauthenticated NodePort UI exposes mutating, cluster-wide endpoints

**Problem:** `deploy/ui.yaml` grants the UI ServiceAccount `patch` on `k8sibackups` (all
namespaces) and `create` on `k8sibackupruns`. `k8si/ui/app.py` backs that with
`POST /api/backups/{ns}/{name}/trigger` and `PATCH /api/backups/{ns}/{name}/paused` — no auth,
no CORS policy — exposed via NodePort on every node's IP at :30080.

Anyone on the network can silently pause every backup (dashboard keeps showing the last stale
`success`) or loop the trigger endpoint across every backup returned by the unauthenticated
`GET /api/backups`. MariaDB backups hold a global FTWRL read lock for up to 300s per snapshot —
this is a one-request DoS against every MariaDB in the cluster.

**Fix:** Split the UI RBAC into a genuinely read-only ClusterRole (`get,list,watch` only).
Put the mutating endpoints behind auth on a separate, namespace-scoped identity — or drop them
from the "read-only dashboard". Replace NodePort with ClusterIP + authenticated Ingress +
NetworkPolicy.

---

### 3. SSRF via `notifyOnFailure`/`notifyOnSuccess` webhook URLs

**Problem:** `deploy/crd.yaml:174-179` defines both webhook fields as unrestricted strings.
`k8si/operator/main.py:115-120` POSTs to them with no scheme/host validation and swallows all
errors. Chained with #2 (UI SA can patch the full backup spec, not just `paused`), an
unauthenticated NodePort request can rewrite the webhook URL and then trigger a backup, making
the operator pod issue attacker-controlled POSTs into the cluster network (cloud metadata
endpoint, kube-apiserver, internal services) — plus exfiltrating failure messages/repo paths in
the payload.

**Fix:** Validate scheme/host in `_notify_webhook`, or require the webhook come from a Secret
reference instead of a free-text spec field. Ship together with #2 — same attack surface.

---

### 4. Unready VolumeSnapshot leaks and permanently wedges the backup

**Problem:** `k8si/operator/workflow.py:258-273` — snapshot creation (phase 1) has no cleanup
on failure, unlike phase 2 (`finally: delete_snapshot_and_pvc`). A single readiness timeout
(`_SNAPSHOT_READY_TIMEOUT=300s`, routine under CSI driver load) leaves an orphaned
VolumeSnapshot. Every subsequent run then blocks for `_SNAPSHOT_CONFLICT_TIMEOUT=1800s` inside
`_wait_no_snapshot_in_progress_sync` before failing — the backup is wedged until someone
manually deletes the leftover object, and each daily retry burns 30 minutes of a thread-pool
worker doing nothing (see #6).

**Fix:** Wrap phase 1 in try/except that deletes the snapshot before re-raising. Extend the
orphan sweep (`_cleanup_orphan_snap_pvcs`) to also cover leftover VolumeSnapshots.

## High

### 5. Job reconciliation is completely inert — wrong Job name

**Problem:** `k8si/operator/main.py:401,491-502` — `run_reconcile_timer` looks up the backup Job
using the **run name**, but the Job is actually named `f"k8si-{name}-{ts2}"` with a *different*
timestamp computed later inside `run_backup` (`workflow.py:213`). The names can never match, so:
stuck-job detection never fires, orphaned Jobs are never deleted (they keep running after their
run is marked Failed), and `backup_timer` can start a second run against the same PVC/repo
because `_has_active_run_sync` doesn't see the zombie Job. A stale test
(`tests/test_operator_main_run_timer.py:465`) baked in the wrong assumption, which is why this
passed review.

**Also:** any backup with `spec.jobTimeout > 3600` is always killed and reported Failed at the
hardcoded 60-minute stuck-run threshold, while its real Job (running under a longer
`activeDeadlineSeconds`) completes successfully unnoticed.

**Fix:** Record the actual Job name in `K8siBackupRun.status` (e.g. `jobName`) when the Job is
created, and have the reconciler read/delete by that.

---

### 6. Shared thread pool exhaustion — likely root cause of the recorded scheduler-hang bug

**Problem:** Long blocking waits (`_wait_job_complete_sync` up to `jobTimeout`/3600s,
`_wait_no_snapshot_in_progress_sync` up to 1800s, `_wait_snapshot_ready_sync` 300s) all run via
`asyncio.to_thread`, which uses the shared default executor
(`ThreadPoolExecutor(min(32, cpu+4))`). There is no cap on concurrent backups — `_running` is
keyed per-backup, so N backups run in parallel, each parking one worker for the full job
duration. Once concurrent backups reach the pool size, every timer's k8s call (including
`backup_timer` and `run_reconcile_timer` themselves) queues behind hour-long sleeps and the
operator looks completely frozen — event loop idle, nothing progressing. This matches
[[bug_scheduler_hang_after_catchup]] exactly, and a post-restart catch-up batch is precisely the
trigger scenario.

**Fix:** Dedicated bounded executor for the polling waits (or replace poll loops with
`kubernetes.watch`/`kubernetes_asyncio`). Add a global semaphore capping concurrent
`run_backup` executions.

---

### 7. Blocking Kubernetes calls made directly on the event loop

**Problem:** `k8si/operator/workflow.py:187,189,196,198` — `_log_phase` inside `run_backup`
calls `_patch_run_status`/`_write_run_log` synchronously (~6 times per backup) without
`asyncio.to_thread`, unlike every other k8s call site in the file. No request timeout is
configured on the k8s client anywhere, so a slow/hung API server blocks the entire operator
event loop indefinitely.

**Fix:** Wrap these calls in `asyncio.to_thread` like the rest of the file. Add a client-level
request timeout.

---

### 8. Operator restart mid-backup starts a duplicate run and deletes the in-flight PVC

**Problem:** `k8si/operator/main.py:548-579` — `on_run_create` only completes after the whole
backup finishes. If the operator restarts mid-run, kopf re-invokes the handler for the same
unfinished run (the `_running` guard is process-local and empty after restart). The re-invoked
`run_backup` calls `_cleanup_orphan_snap_pvcs`, which deletes the ephemeral PVC the *original*
still-running Job is mounting, then creates a second snapshot/Job — two Jobs writing to the same
repository concurrently.

**Fix:** Before executing, re-read the run's live status and refuse if already Running with a
live Job. Scope orphan cleanup to exclude PVCs currently mounted by a running pod.

---

### 9. Stored XSS via unescaped `'` in dashboard onclick handlers

**Problem:** `escapeHtml()` in `k8si/ui/dashboard.html` doesn't escape `'`, and its output is
spliced into single-quoted JS string literals inside `onclick="..."` attributes
(`buildStatusBadge`, `buildSparkline`, `buildRow`). `status.lastRunRef` and
`recentRuns[].name` are unrestricted CRD strings (`deploy/crd.yaml`), and the UI's own
ServiceAccount can patch them (per #2) — giving an unauthenticated stored-XSS chain, e.g.
`lastRunRef: x');alert(document.cookie);//`.

**Fix:** Stop building `onclick` strings from data. Use `data-*` attributes and one delegated
event listener instead.

---

### 10. Cluster-wide `pods/exec` + `secrets: get` is a privilege-escalation primitive

**Problem:** `deploy/rbac.yaml:35-43`, bound cluster-wide. `create` on `pods/exec` in all
namespaces lets a compromised operator identity exec into any higher-privileged pod cluster-wide
and inherit its identity; paired with cluster-wide `secrets: get`, a single operator RCE
harvests every credential in the cluster. Actual need is one secret read
(`quiesce.py:18`) and exec only for the sqlite backend's quiesce path.

**Fix:** Move `secrets`/`pods/exec` into per-namespace Roles scoped to namespaces that actually
have a K8siBackup. Drop `pods/exec` entirely for deployments not using the sqlite backend.

---

### 11. Everything runs as root, no securityContext anywhere

**Problem:** Neither Dockerfile sets `USER`; neither Deployment sets a pod/container
`securityContext`. Applies to the operator, the UI (behind an unauthenticated NodePort per #2),
and every backup Job — which mounts production PVCs as uid 0.

**Fix:** Add `runAsNonRoot`, non-root uid, `allowPrivilegeEscalation: false`,
`readOnlyRootFilesystem: true`, drop all capabilities, `seccompProfile: RuntimeDefault` to all
three workload types. (Restore init container's root chmod for SSH perms is a justified
exception.)

---

### 12. PVC/PV cleanup uses unguarded prefix matching — can delete another backup's data

**Problem:** Two related bugs, same root cause:
- `k8si/operator/workflow.py:151-166` (`_cleanup_orphan_snap_pvcs`) matches
  `k8si-snap-{name}-` as a string prefix. Backups named `app` and `app-db` in the same
  namespace collide — starting `app` deletes `app-db`'s live in-flight ephemeral PVC.
- `k8si/operator/snapshot.py:153` (`_delete_pvc_sync`) deletes whatever PV is bound to a PVC
  with no reclaim-policy check and no ownership check — unrecoverable for `Retain`-policy
  volumes.
- `deploy/rbac.yaml:29-31` grants this cluster-wide `persistentvolumes: delete`.

**Fix:** Match the full timestamp pattern (or better, label ephemeral PVCs
`k8si.io/backup={name}` and select on the label). Verify `Retain` policy + ownership label
before deleting a PV.

---

### 13. Shell injection via `spec.database.dbPaths` in sqlite quiesce

**Problem:** `k8si/operator/quiesce.py:78` — `["sh", "-c", f"sqlite3 {db_path} ..."]`, unquoted
interpolation of a free-form CRD string, executed via pod exec with the operator's cluster-wide
exec permission. The safe `python3 -c` path is tried first but falls through to this on any
image without python3. Exec failures are silently swallowed on both paths.

**Fix:** Use argv form (`["sqlite3", db_path, "PRAGMA ..."]`), no shell. Validate `dbPaths`
against an absolute-path pattern in the CRD schema.

---

### 14. UI Logs button: same class of bug as the lastRunRef fix, several instances

**Problem:** `k8si/ui/dashboard.html` — a family of bugs from tab state not carrying the backup
name / not being reconciled against `activeRunState`:
- Closing a log tab before completion strands `activeRunState` forever — row frozen, 3s fast-poll
  runs indefinitely.
- `openBackupLogs` can show a stale completed run while a new one is actually live (mirror image
  of the bug fixed in 437bbfa — `recentRuns` checked where `lastRunRef`/`activeRunState` should
  win during an active run).
- The legacy per-backup log path (`openLogs`) is dead code — its only writer
  (`workflow._write_run_log`) has no callers, and the UI SA lacks the RBAC to read pod logs
  anyway. It runs a silent 10-minute timeout then paints a **green** "success" dot.
- No cap on concurrent SSE tabs; enough open tabs starve the dashboard's own `/api/backups`
  polling (~6 connections per origin on HTTP/1.1).
- Run picker breaks after selecting an older run from a currently-live backup (empty backup name
  propagates through, picker disappears).

**Fix:** Store `backupName` directly on the tab object instead of re-deriving it from
`recentRuns` scans (fixes several of the above at once). Cap SSE iterations like the legacy
endpoint. Decide whether the legacy path is deleted or properly wired up (RBAC + writer).

## Medium

- **`k8si-restore` ClusterRole is defined but never bound** (`deploy/rbac.yaml:67-74`) — restore
  status writes (`lastRestoreResult` etc.) 403 in every real deployment.
- **UI manifests target namespace `k8si`, RBAC creates `k8si-system`** — `kubectl apply -f
  deploy/` fails out of the box unless the namespace is created out-of-band.
- **`K8SI_IMAGE` pinned to `latest`** (`deploy/operator.yaml`) for every backup Job, which runs
  as root against production PVCs — no reproducibility, no audit trail for a tag repush. Pin to
  the operator's version, ideally by digest.
- **No liveness/readiness probes on the operator**, 128Mi memory limit for a cluster-wide watch
  cache — directly relevant to the scheduler-hang bug (#6): a hung operator looks "Running" and
  healthy in kubectl indefinitely.
- **CRD validation gaps** (`deploy/crd.yaml`): no cross-field requirement that at least one of
  `resticSecret`/`kopiaSecret`/`repositoryPVC` is set; `pvc`/secret refs not immutable (changing
  them silently repoints a repo at a different dataset); `schedule` has no cron pattern; retention
  counts and `jobTimeout`/`maxRetriesPerDay` have no `minimum`; `status.recentBackups`/`recentRuns`
  have no `maxItems` (and are reachable via the unauthenticated status-patch RBAC in #2 — a
  multi-MB status patch can permanently wedge a K8siBackup against the ~1.5MB etcd object limit).
- **`_update_parent_backup` read-modify-write races** (`main.py:583-590,710-765`) — an hour-stale
  snapshot of `status` can silently discard concurrent history writes from the reconciler, or
  flip a just-succeeded backup back to `failed` by reconciling a stale run.
- **`_find_pvc_node_sync` can pin a Job to a node from a terminated pod** (`workflow.py:326-337`)
  — no phase filter — reproducing the "block for an hour with no diagnosis" symptom
  `_wait_pvc_bound_sync` was removed to fix, by a different path.
- **Kopia snapshot ID truncated to 8 chars for restore** (`restore.py:152-153`,
  `kopia.py:126,194,205`) — restic-style short-ID convention doesn't apply to kopia's manifest
  IDs; inconsistent with `verify_snapshot`, which correctly uses the full ID.
- **`RESTIC_PASSWORD_FILE` silently ignored by kopia backend** (`kopia.py:28`) — opaque connect
  failure when only the file-based secret form is configured.
- **`spec.backendType` defined in the CRD, never read anywhere** — actual backend is only ever
  the operator pod's env var; setting `backendType: kopia` against a restic-configured operator
  silently does a restic backup and reports a contradictory `backendType` on the run.
- **`K8siBackupRun` objects are never pruned** — accrue forever (365/year for a daily backup),
  each carries its own 60s reconcile timer indefinitely.
- **Blocking custom-object calls without `asyncio.to_thread`** in `k8si/ui/app.py:240,322` —
  stall the whole UI event loop, including in-flight SSE streams, during every tab open.
- **`successRate`/streak computed from a different array than the sparkline** (`app.py:102-103`
  uses `recentBackups`, dashboard renders `recentRuns` when present) — can disagree for any CR
  predating `recentRuns` or a partial patch.
- **Trigger endpoint is CSRF-able** — no custom header requirement, so it's a CORS simple
  request; any page an operator visits can POST-trigger backups cross-origin.
- **`spec.resources` passthrough with no bounds** (`crd.yaml:180-182`) into the backup Job pod
  spec — can create an unschedulable or unbounded pod.

## QA / testing gaps

Coverage run: 476 tests, **96% overall** line coverage. The unit suite is genuinely good — real
negative-path tests throughout, not mock theater. Three gaps stand out:

1. **Kopia has zero exercise in the e2e suite.** All 6 e2e scenarios hard-code restic secrets.
   Kopia only ever runs against a mocked CLI, so a real CLI-output-format change (exactly the
   parsing code at issue in the "Medium" kopia findings above) would ship undetected.
2. **Operator reconciliation error branches are untested** — flagged independently by the QA
   review before it saw the code-review results, and this is precisely the code containing the
   Job-name-mismatch bug (#5) and the restart-duplication bug (#8) above. The coverage gap and
   the real bug are the same code paths.
3. **`dashboard.html` has no behavioral test coverage** — `tests/test_dashboard_html.py` is 57
   lines of source-text regex assertions (checks a function body contains a substring in the
   right order), not real DOM/SSE/tab-lifecycle testing. Reasonable given no build tooling
   exists, but real — it's why bug family #14 above shipped with no test able to catch it. A
   lightweight headless-browser smoke test (Playwright, a couple of key flows) would close the
   actual risk surface without requiring a JS build pipeline.
4. **UI SSE/live-log-tailing code is the least-covered module (85%)** — the live pod-log-tailing
   branch (`app.py:365-379`) has zero test coverage; it's also currently masked by missing RBAC
   (item in Medium list above), so a fix to one needs a test added for the other.

## Suggested sequencing

1. **#1 + #2 + #3 together** — same class of "silent/unauthenticated failure that looks
   healthy", and #2+#3 are literally the same attack chain. Highest risk, most self-contained.
2. **#4, #5, #6** — the wedge/reconciliation/thread-pool cluster. #6 likely *is* the recorded
   scheduler-hang bug; worth confirming before writing new code for it.
3. **#9, #10, #11, #12, #13** — hardening pass, mostly manifest/RBAC changes plus one small
   Python fix each (quiesce.py, snapshot.py, workflow.py prefix match).
4. **#7, #8, #14** — correctness fixes, no security dimension, can ride along with whichever of
   the above touches the same file.
5. **Medium list + QA gaps** — grab opportunistically alongside the above; the kopia e2e gap and
   the reconciliation-timer test gap are worth closing early since they'd have caught #5 and the
   kopia bugs directly.
